# clippy `double_must_use` on `#[async_trait]` traits under rustc 1.99 — design

Date: 2026-10-13
Status: DRAFT
Source: savvagent/otto-cli#186

## Brief

Issue #186 (bug), verbatim acceptance criteria:

- `RUSTFLAGS="-D warnings" cargo +1.99.0 clippy --workspace --all-targets` is clean
- The fix either addresses the lint at the `#[async_trait]` sites (an `allow` with a reason, or a
  newer `async-trait` if one stops emitting the attribute) or pins CI's toolchain. The PR says
  which and why.
- The `known red` entry for the lint gate in `CLAUDE.md`'s Development Workflow section is removed
  in the same PR

CI's `fmt + clippy` job installs `dtolnay/rust-toolchain@stable` (rustc 1.99.0 since 2026-09-28).
Clippy 1.99 denies `clippy::double_must_use` on the trait method declarations that `#[async_trait]`
expands in `crates/otto-mcp/src/lib.rs` (`:31`, `:63`, `:91`) and `crates/otto-plugin/src/`
(`content.rs:161`, `in_process_tool.rs:19`, `plugin.rs:24`, `screen.rs:13`).

## Premise corrections

- The `#[must_use]` is not written in this repo: `grep -rn must_use crates/otto-mcp
  crates/otto-plugin` finds nothing. `async-trait` 0.1.89 (the locked version) pushes a bare
  `#[must_use]` onto every trait method without a default body (`src/expand.rs:69`), and the
  expanded signature returns `Pin<Box<dyn Future<…>>>`, which is already `#[must_use]` through
  `Future`. There is no attribute in our source to remove.
- `async-trait` 0.1.92 (latest on crates.io) no longer emits that attribute (no `must_use` in its
  `src/`). With only the lockfile bumped to 0.1.92, `RUSTFLAGS="-D warnings" cargo +1.99.0 clippy
  --workspace --all-targets --keep-going` exits 0 across the whole workspace, so the "more
  findings may appear" concern in the issue does not materialize.

## Assumptions

- **Fix choice: upgrade `async-trait`, not `#[allow]`, not a toolchain pin.** It removes the
  redundant attribute at its source (the macro), needs no suppression on the seven affected traits, and keeps CI
  on floating `stable`, which is how the repo catches new lints early. An `allow` would hide the
  lint for hand-written code in those modules too; a pin would freeze every lint. The PR body carries this rationale (AC 2).
- **Raise the workspace requirement to `async-trait = "0.1.92"`** in the root `Cargo.toml`, not
  only the lockfile, so a `cargo update --precise` or a fresh resolution can never select a version
  that re-emits the attribute. `Cargo.lock` is regenerated by `cargo update -p async-trait`.
- `async-trait` 0.1.92 depends on `syn` 3 (added to the lockfile next to `syn` 2). Both declare
  `rust-version = 1.71`, below the workspace MSRV 1.89, so the MSRV holds. It is a compile-time
  proc-macro dependency only; nothing it pulls in links into the binaries.
- Release: PATCH (fix, no public-interface change) → v0.30.11, cut after merge per the section.

## Goal & Success Criteria

Make the lint gate green on CI's floating stable (rustc 1.99) without suppressions, and retire
the #186 known-red entries.

- `RUSTFLAGS="-D warnings" cargo +stable clippy --workspace --all-targets` exits 0 on rustc 1.99.0
- The same command still exits 0 on rustc 1.95.0 (the previous local toolchain)
- fmt, build, test, and `dist plan` gates pass; CI `fmt + clippy` passes on the PR head
- No `#[allow(clippy::double_must_use)]` anywhere in the tree
- `CLAUDE.md` Development Workflow has no `known red` or `merge gate known red` entry for #186

## Scope

In: root `Cargo.toml` `async-trait` requirement, `Cargo.lock`, this spec and its plan, and four
lines of `CLAUDE.md`'s Development Workflow section: the Gates `known red` bullet (deleted), the
Gates `toolchain` bullet (drop "as of #186" and "clean on 1.95"), the "clean on 1.95 and red on

`merge gate known red` bullet (deleted).

Out: pinning the CI toolchain; any change to trait definitions or signatures; other dependency
upgrades; CHANGELOG (the release PR adds the entry).

## Architecture

No code changes. The `#[async_trait]` traits (`otto-mcp`: `ProviderClient`, `ProviderHandler`,
`StreamEmitter`; `otto-plugin`: `ContentRenderer`, `InProcessToolHandler`, `Plugin`, `Screen`) and
every other `#[async_trait]` use in the workspace expand identically except for the dropped
`#[must_use]`. The returned boxed future stays `#[must_use]` via `Future`, so an unawaited
call still warns (`unused_must_use`). No public interface changes; the provider traits and the
plugin ABI are source- and behavior-identical.

## Invariants impact

- Everything is MCP-shaped; turn loop in `Host`; locks across `.await`; provider pool; forwarder
  aborts; secrets; tool reach: untouched (no code change).
- Public interfaces change additively: no interface change at all.
- `otto-plugin-wit` leaf / `otto-plugin` WIT-portable: neither crate's `Cargo.toml` changes;
  `async-trait` is already an `otto-plugin` dependency and is not on either guard list.
- No `unwrap()` added.

## Error Handling & Edge Cases

- A downstream that pins `async-trait` below 0.1.92 now fails resolution; `release-plz.toml` sets
  `publish = false`, so there are no known downstreams.

## Testing Approach

The lint gate is the test: before the change it fails on 1.99 with 5 (`otto-mcp`) + 6 (`otto-plugin`) `double_must_use` errors
on the methods of the seven traits listed in the Brief (several traits have more than one method),
(reproduced); after, it passes. Then the full gate set: fmt, lint (1.99 and 1.95), build, test,
and `dist plan` (Cargo.toml changed). The plugin-example gate does not apply (no
`examples/plugin-hello-*` or `otto-plugin-wit` change); the plugin ABI smoke pre-merge check does
not apply (no file under `crates/otto-plugin*/` changes).

## Risks & Open Questions

- `syn` 3 increases cold build time slightly (one more proc-macro parser). Accepted.
